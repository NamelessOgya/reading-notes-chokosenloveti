# Towards General Text Embeddings with Multi-stage Contrastive Learning (GTE)

**arXiv:** 2308.03281  
**著者:** Zehan Li, Xin Zhang, Yanzhao Zhang, Dingkun Long, Pengjun Xie, Meishan Zhang（Alibaba DAMO Academy）  
**発表:** 2023年8月

---

## 背景

テキスト埋め込みモデルの研究は従来、特定タスク（STS や密検索）に特化したモデルが主流だった。

- **SimCSE**：対称ペアで学習 → 検索タスクに弱い
- **DPR 系**：密検索に特化 → STS タスクに弱い

近年の流れとして E5 など「大規模弱教師ありデータによる汎用埋め込みモデル」が台頭しているが、**独自の非公開データを使うものが多く**再現性に乏しい。

GTE は**オープンソースデータのみ**を使い、シンプルな多段階対照学習でこれを凌駕することを目指した。

---

## 手法

### 全体パイプライン

```
Stage 1: 教師なし対照事前学習（~800M テキストペア）
          ↓
Stage 2: 教師あり対照 Fine-tuning（~3M アノテーション付きペア）
```

---

### モデルアーキテクチャ

- **バックボーン**: BERT（small/base/large の3スケール）
  - small: MiniLM（30M）
  - base: BERT-base（110M）
  - large: BERT-large（330M）
- **プーリング**: Mean Pooling（[CLS] トークンを使わない）
- **プーラー層なし**

---

### Stage 1: 教師なし事前学習データ

約 **800M テキストペア**（フィルタリングなし）をオープンソースから収集。

| カテゴリ | ソース例 | ペアの作り方 |
|---|---|---|
| ウェブページ | CommonCrawl, ClueWeb | タイトル ↔ 本文 |
| 学術論文 | arXiv, SemanticScholar | タイトル ↔ アブスト |
| コミュニティ QA | StackExchange | 質問 ↔ 回答 |
| ソーシャルメディア | Reddit | 投稿 ↔ コメント |
| 知識ベース | Wikipedia, DBPedia | タイトル ↔ 記事 |
| コード | StackOverflow, GitHub | コメント ↔ コード |
| ハイパーリンク | 各種 | リンク元文 ↔ リンク先文 |

**合計 33 データセット**を使用（E5 の CCPairs と異なり**フィルタリングなし**）。

---

### Stage 2: 教師あり Fine-tuning データ

約 **3M アノテーション付きペア**（複数先行研究のデータを統合）。

| カテゴリ | データセット例 |
|---|---|
| ウェブ検索 | MS MARCO |
| オープン QA | Natural Questions |
| 自然言語推論 | SNLI |
| 事実検証 | FEVER |
| 言い換え | Quora |

ハード負例は外部リトリーバーでマイニング。

---

### 学習の工夫

#### ① 改良対照損失（GTE 提案）

通常の InfoNCE 損失（一方向：クエリ → ドキュメント）を**双方向・4方向**に拡張。

バッチ内ポジティブペア $\{(q_i, d_i)\}_{i=1}^{N}$ に対し：

$$\mathcal{L} = \mathcal{L}_{q \to d} + \mathcal{L}_{d \to q}$$

各方向の損失はバッチ内の**クエリとドキュメント両方**をネガティブプールとして使用：

| ペア | 目的 |
|---|---|
| クエリ → ドキュメント | 正例ドキュメントを他の全ドキュメント・クエリから区別 |
| ドキュメント → クエリ | 正例クエリを他の全ドキュメント・クエリから区別 |

温度 $\tau = 0.01$ 固定。これにより**固定バッチサイズでも実質的なネガティブ数が2倍**になる。

#### ② タスク均質バッチ（Task-homogeneous Batching）

同一バッチ内は**必ず同一データソースのサンプルのみ**を含める。

- モデルがデータソース固有の特徴でスコアリングする「ショートカット学習」を防止
- E5・Ruri も同様の戦略を採用（GTE が起点）

#### ③ データサンプリング（温度付き多項分布）

800M ペアはデータセットごとにサイズが大きく異なるため、**温度付き多項分布**でサンプリング：

$$p_i \propto n_i^{\alpha}, \quad \alpha = 0.5$$

- $\alpha = 0$：一様サンプリング（小規模データセットを過剰に使う）
- $\alpha = 1$：比例サンプリング（大規模データセットに偏る）
- $\alpha = 0.5$：中間でバランスが最良（アブレーションで検証済み）

#### ④ スケールごとのハイパーパラメータ

| パラメータ | Stage 1（事前学習） | Stage 2（Fine-tuning） |
|---|---|---|
| バッチサイズ | ~10,000 以上 | 128 |
| ネガティブ数 | バッチ内（in-batch） | 15（ハード負例含む） |
| 最大系列長 | 128 | 512 |
| 学習ステップ | 50,000（~1 エポック） | 1 エポック |
| Optimizer | AdamW + linear decay | AdamW（学習率 1/10） |
| 精度 | fp16 | fp16 |

## 実験結果

### BEIR（ゼロショット検索、nDCG@10 平均）

| モデル | パラメータ | Avg. |
|---|---|---|
| BM25 | - | 43.0 |
| Contriever | 110M | 42.5 |
| E5-base | 110M | 46.1 |
| **GTE-base** | **110M** | **~47** |
| E5-large | 330M | ~47 |
| **GTE-large** | **330M** | **~49** |

→ GTE-base（110M）が E5-large（330M、3倍のパラメータ）と同等性能を達成

### MTEB（英語・56データセット平均）

| モデル | Avg. |
|---|---|
| OpenAI text-embedding-ada-002 | 60.99 |
| E5-large | 62.25 |
| **GTE-base（110M）** | **62.35** |
| **GTE-large（330M）** | **63.13** |

→ **GTE-base が OpenAI 商用 API を上回った**

### CodeSearchNet（コード検索）

言語ごとに個別 Fine-tuning された CodeBERT 系モデルを、**全言語一括評価**で GTE-base が上回る。プログラミング言語をテキストとして扱うだけでコード固有の構造知識なしに高性能を達成。

## 分析（アブレーション）

### データ多様性の影響（Section 5.1）

事前学習・Fine-tuning の両フェーズで、データセット数が増えるほど MTEB スコアが向上。**「データの多様性はデータ量と同等以上に重要」**

### バッチサイズの影響

| バッチサイズ | 性能 |
|---|---|
| 小（~1k） | 低 |
| ~10,000 | 飽和（ピーク） |
| 10,000 超 | **改善なし** |

→ 事前学習のバッチサイズは ~10,000 で飽和。Ruri・E5 はこの知見を引用し 8,192 を採用。

### 多段階学習の効果（Section 5.3）

| 設定 | Retrieval | Avg |
|---|---|---|
| Fine-tuning のみ | 最低 | 最低 |
| **事前学習のみ** | **中** | **中（FT単体より高い）** |
| **事前学習 + Fine-tuning** | **最高** | **最高** |

**直感に反する発見：事前学習単体 > supervised fine-tuning 単体**。大規模な弱教師あり事前学習の重要性を示す。

### 改良対照損失の効果（Section 5.5）

| 損失関数 | 事前学習 | FT後 |
|---|---|---|
| 通常 InfoNCE（一方向） | 低 | 低 |
| **改良対照損失（GTE、双方向）** | **高** | **最高** |

改良損失は事前学習・Fine-tuning の**両フェーズで**一貫して有効。

### データ混合比 α の影響（Section 5.4）

| α | Retrieval | STS | Avg |
|---|---|---|---|
| 0.0（一様） | 低 | 中 | 低 |
| **0.5（最適）** | **最高** | **最高** | **最高** |
| 1.0（比例） | 中 | 低 | 中 |

## 貢献と限界

**貢献:**
- オープンソースデータのみで OpenAI 商用 API（ada-002）を MTEB で上回った汎用埋め込みモデルを構築
- **改良対照損失（双方向・4方向）を提案**→ Ruri・E5 などに広く採用
- タスク均質バッチの有効性を実証
- コードデータをテキストとして扱い、言語特化 Fine-tuning 不要のコード検索を実現

**限界:**
- 最大系列長 512 トークン（長文非対応）
- 英語モデルのみ（多言語対応なし）
- 大規模事前学習によるデータ汚染（exact match 以外でのチェック未実施）
- 非因果（双方向アテンション）アーキテクチャのみ
